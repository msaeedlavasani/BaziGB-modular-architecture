# Game Rules Contract

Status: Accepted contract · Backgammon pilot implemented · 2026-08-27

This contract separates game correctness from UI, transport, persistence, AI, and visual presentation. A game rule change must remain local to the game package unless its public contract genuinely changes.

## Anatomy of a game module

Each `packages/games/<game>` package owns:

1. **State and move types** — the canonical vocabulary of the game.
2. **Pure rules** — initial state, legal actions, validated transitions, win conditions, and serialization.
3. **Invariants** — facts that must hold after every legal transition, such as checker conservation.
4. **Undo policy** — which actions are reversible. Random outcomes and committed online actions are not assumed reversible.
5. **AI policy** — move selection over legal actions; it may not redefine legality.
6. **Conformance tests** — examples, edge cases, exploit regressions, and invariant/property tests.

The shared engine defines only the cross-game contract. The server owns authoritative multiplayer sequencing, identity, persistence, reconnect, and protocol validation. The web app owns presentation and offline/local-session continuity; it must not duplicate rules.

## Required correctness properties

- Every submitted action is validated by the game package before mutation.
- Random results are generated once, persisted immediately, and cannot be regenerated by refresh.
- Undo eligibility comes from the game package through `canUndoMove`; transport and UI cannot guess it.
- Multi-action turns use the versioned `Turn Transaction Contract`; a final draft move does not implicitly commit the turn.
- Serialized state preserves all rule-relevant data, including captured pieces, bars, hands, turn, phase, and unresolved random results.
- A reconnect or refresh restores the same committed state.
- Piece/card/token inventories are conserved unless a documented rule explicitly creates or removes them.
- The server remains authoritative for online and competitive play. Client persistence is continuity, not an anti-cheat boundary.

## Change workflow

Before changing a game:

1. Record the rule and affected invariant.
2. Add a failing regression or invariant test in that game package.
3. Change the pure rule implementation.
4. Run the game package tests and shared engine checks.
5. Verify local refresh and online reconnect when persistence is involved.
6. Change presentation only after the canonical state is proven correct.

## Guided Play extension point

Guided Play is a presentation of canonical legal actions, not a second rules engine. A future optional adapter capability may return explanations and visual emphasis for legal actions. It must be deterministic for the same public state, reveal no private opponent data, and remain switchable without changing game state. Entitlement or monetization belongs outside the rules package.

## Current Backgammon guarantees

- A second roll while dice are unresolved is rejected.
- Rolling dice is not undoable.
- Refresh restores an unresolved local roll.
- A hit moves the opponent checker to the bar and serialization preserves it.
- Legal moves preserve fifteen checkers per player across points, bar, and borne-off totals.
- A completed game has an explicit `roundEnd` boundary; the next game starts only after acknowledgement.
- Undo history cannot cross a completed-game or completed-match boundary.
- Backgammon turn transactions follow `docs/turn-transaction-contract.md`; implementation is tracked separately from this accepted contract.
- Match scoring distinguishes single, gammon and backgammon results.
- Match play supports target scores 3/5/7/9/11/13, cube ownership, Crawford and dead-cube restrictions.
- The game adapter, not the web page or server, owns the transition to the next game.

## Deliberate Backgammon limitations

The current profile must not yet be described as a complete tournament implementation. Resignation, a dedicated opening-roll procedure, Jacoby/beaver variants, match clocks, and automatic adjudication of every federation-specific irregularity are not implemented. These require separate sourced decisions and conformance tests before UI controls are added.
